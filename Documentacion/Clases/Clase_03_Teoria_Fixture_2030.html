🌐Introducción a Sistemas Distribuidos

¿Qué es un Sistema Distribuido?

Un sistema distribuido es una colección de computadoras independientes que aparecen ante los usuarios como un sistema único y coherente. En el contexto de bases de datos, esto significa que los datos y el procesamiento se distribuyen a través de múltiples nodos o servidores.

Definición Formal

Según Leslie Lamport: "Un sistema distribuido es aquel en el que el fallo de una computadora de la que nunca has oído hablar puede hacer que tu propia computadora sea inutilizable."

¿Por qué Sistemas Distribuidos en Bases de Datos?

🚀 Escalabilidad

Manejar volúmenes de datos que exceden la capacidad de un solo servidor. Ejemplos: Facebook (2.8 mil millones de usuarios), Google (8.5 mil millones de búsquedas diarias).

⚡ Performance

Distribuir la carga de trabajo entre múltiples nodos para reducir latencia y aumentar throughput. Paralelización de consultas y operaciones.

🛡️ Disponibilidad

Eliminar puntos únicos de falla. Si un nodo falla, otros pueden continuar operando. Uptime de 99.99% o superior.

🌍 Distribución Geográfica

Acercar los datos a los usuarios finales para reducir latencia. CDNs y réplicas regionales.

Desafíos Fundamentales

1. FALLOS DE RED (Network Partitions) - Las redes pueden fallar impredeciblemente - Los nodos pueden quedar aislados - Imposible distinguir entre nodo lento y nodo caído 2. LATENCIA VARIABLE - Comunicación entre nodos toma tiempo - Latencia puede variar significativamente - Timeouts son difíciles de configurar correctamente 3. CONCURRENCIA DISTRIBUIDA - Múltiples nodos modificando datos simultáneamente - Sincronización es costosa y compleja - Race conditions distribuidas 4. CONSISTENCIA DE DATOS - Mantener datos sincronizados entre nodos - Propagación de cambios toma tiempo - Conflictos de actualización 5. CONSENSO DISTRIBUIDO - Acordar sobre el estado del sistema - Algoritmos como Raft, Paxos - Complejidad exponencial con número de nodos

Evolución: De Monolítico a Distribuido

⚖️Teorema CAP (Brewer's Theorem)

Definición del Teorema

Formulado por Eric Brewer en 2000, el Teorema CAP establece que en un sistema distribuido es imposible garantizar simultáneamente las tres propiedades siguientes:

Análisis Detallado de cada Propiedad

🔄 Consistency (Consistencia)

Definición: Todos los nodos ven los mismos datos al mismo tiempo. Una lectura recibe la escritura más reciente o un error.

Ejemplo: Si escribes "saldo = $100" en un nodo, todos los demás nodos deben mostrar inmediatamente "$100" o fallar.

Implicación: Requiere sincronización entre nodos antes de confirmar operaciones.

⚡ Availability (Disponibilidad)

Definición: El sistema permanece operativo 100% del tiempo. Toda solicitud recibe una respuesta (sin garantizar que sea la más reciente).

Ejemplo: Puedes leer el saldo incluso si algunos nodos están caídos, aunque el valor puede estar desactualizado.

Implicación: Los nodos deben responder independientemente del estado de otros nodos.

🌐 Partition Tolerance (Tolerancia a Particiones)

Definición: El sistema continúa operando a pesar de fallos arbitrarios de comunicación entre nodos.

Ejemplo: Si la red se divide y algunos nodos no pueden comunicarse, el sistema sigue funcionando.

Implicación: En sistemas distribuidos reales, las particiones son inevitables.

Combinaciones Posibles (Pick 2)

CP (Consistency + Partition Tolerance) ├── Ejemplo: MongoDB con escrituras majority ├── Comportamiento: Durante partición, algunos nodos se vuelven read-only ├── Ventaja: Datos siempre consistentes └── Desventaja: Pérdida de disponibilidad durante particiones AP (Availability + Partition Tolerance) ├── Ejemplo: Cassandra, DynamoDB ├── Comportamiento: Todos los nodos siguen operando durante particiones ├── Ventaja: Sistema siempre disponible └── Desventaja: Datos pueden estar temporalmente inconsistentes CA (Consistency + Availability) ├── Ejemplo: Bases de datos relacionales tradicionales (PostgreSQL, MySQL) ├── Comportamiento: Perfecta consistencia y disponibilidad ├── Ventaja: Modelo familiar y predecible └── Desventaja: No tolera particiones (no es verdaderamente distribuido)

Casos de Uso por Combinación

Combinación Casos de Uso Ideales Tecnologías Ejemplo Trade-offs
CP Sistemas financieros, inventarios, transacciones críticas MongoDB, Redis Cluster, HBase Disponibilidad sacrificada por consistencia
AP Redes sociales, catálogos, sistemas de recomendación Cassandra, DynamoDB, CouchDB Consistencia eventual, posibles conflictos
CA Aplicaciones tradicionales, sistemas internos PostgreSQL, MySQL, SQL Server No escalable horizontalmente

⚠️ Aclaración Importante

El teorema CAP no significa que siempre debes elegir solo 2 de 3. En la práctica, puedes ajustar el nivel de cada propiedad según las necesidades. Por ejemplo, "eventual consistency" vs "strong consistency", o "99.9%" vs "99.99%" de disponibilidad.

🔄Modelos de Consistencia

Espectro de Consistencia

La consistencia no es binaria (todo o nada), sino que existe un espectro de modelos, cada uno con diferentes garantías y trade-offs:

STRONG CONSISTENCY (Consistencia Fuerte) ├── Linearizability: Operaciones parecen instantáneas y atómicas ├── Sequential Consistency: Operaciones en orden secuencial global └── Causal Consistency: Operaciones causalmente relacionadas mantienen orden WEAK CONSISTENCY (Consistencia Débil) ├── Eventual Consistency: Eventualmente todos los nodos convergen ├── Session Consistency: Consistencia dentro de una sesión de usuario └── Monotonic Consistency: Una vez que se ve un valor, no se ven valores anteriores

Modelos Principales en Bases de Datos

🔒 Strong Consistency

Garantía: Todas las lecturas reciben la escritura más reciente.

Implementación: Sincronización antes de confirmar escrituras.

Ejemplo: Transferencia bancaria debe ser visible inmediatamente en todos los nodos.

Costo: Mayor latencia, menor disponibilidad.

⏳ Eventual Consistency

Garantía: Si no hay nuevas escrituras, eventualmente todos los nodos convergen.

Implementación: Propagación asíncrona de cambios.

Ejemplo: Actualización de perfil en red social puede tardar segundos en propagarse.

Costo: Posibles inconsistencias temporales.

📱 Session Consistency

Garantía: Dentro de una sesión, las lecturas son consistentes con las escrituras previas.

Implementación: Sticky sessions o tokens de consistencia.

Ejemplo: Usuario ve inmediatamente su propio post, otros pueden tardar.

Costo: Complejidad en balanceadores de carga.

🔗 Causal Consistency

Garantía: Operaciones causalmente relacionadas se ven en el mismo orden.

Implementación: Vector clocks o timestamps lógicos.

Ejemplo: Si comentas un post, otros ven el post antes que el comentario.

Costo: Overhead de tracking causal.

Ejemplo Práctico: Red Social

Escenario: Juan publica una foto y María la comenta STRONG CONSISTENCY: 1. Juan publica foto → Espera confirmación de todos los nodos 2. María ve la foto → Garantizado que es la versión más reciente 3. María comenta → Espera confirmación de todos los nodos 4. Otros usuarios ven foto + comentario simultáneamente Resultado: Latencia alta, pero perfecta consistencia EVENTUAL CONSISTENCY: 1. Juan publica foto → Confirmación inmediata, propagación asíncrona 2. María ve la foto → Puede ser versión antigua o nueva 3. María comenta → Confirmación inmediata 4. Otros usuarios ven cambios gradualmente (segundos/minutos) Resultado: Latencia baja, posibles inconsistencias temporales CAUSAL CONSISTENCY: 1. Juan publica foto → Propagación con timestamp causal 2. María ve la foto → Registra dependencia causal 3. María comenta → Comentario marcado como dependiente de la foto 4. Otros usuarios ven foto antes que comentario (orden causal preservado) Resultado: Balance entre performance y consistencia lógica

⚡ACID vs BASE

Dos Filosofías Opuestas

ACID y BASE representan dos enfoques fundamentalmente diferentes para el manejo de datos en sistemas distribuidos:

🔒 ACID

Atomicity: Todo o nada

Consistency: Estado válido siempre

Isolation: Transacciones independientes

Durability: Cambios permanentes


Filosofía: "Mejor estar seguro que lamentarse"

Enfoque: Consistencia sobre disponibilidad

🌊 BASE

Basically Available: Sistema siempre responde

Soft state: Estado puede cambiar sin input

Eventual consistency: Consistencia en el tiempo


Filosofía: "Es mejor estar aproximadamente correcto que exactamente equivocado"

Enfoque: Disponibilidad sobre consistencia

Análisis Detallado: ACID

⚛️ Atomicity (Atomicidad)

Principio: Las transacciones son indivisibles - se ejecutan completamente o no se ejecutan.

-- Transferencia bancaria BEGIN TRANSACTION; UPDATE cuentas SET saldo = saldo - 100 WHERE id = 'cuenta_a'; UPDATE cuentas SET saldo = saldo + 100 WHERE id = 'cuenta_b'; COMMIT; -- Solo si ambas operaciones son exitosas -- Si cualquier operación falla → ROLLBACK automático

Implementación: Write-ahead logging (WAL), two-phase commit (2PC)

🎯 Consistency (Consistencia)

Principio: La base de datos siempre está en un estado válido según las reglas de negocio.

-- Reglas de negocio como constraints ALTER TABLE cuentas ADD CONSTRAINT saldo_positivo CHECK (saldo >= 0); -- La transacción falla si viola constraints UPDATE cuentas SET saldo = -50 WHERE id = 'cuenta_a'; -- ERROR: violates check constraint "saldo_positivo"

Implementación: Constraints, triggers, validaciones

🔐 Isolation (Aislamiento)

Principio: Las transacciones concurrentes no se interfieren entre sí.

-- Niveles de aislamiento READ UNCOMMITTED -- Dirty reads posibles READ COMMITTED -- Solo datos confirmados REPEATABLE READ -- Mismos datos en múltiples lecturas SERIALIZABLE -- Ejecución secuencial simulada -- Ejemplo de problema sin aislamiento: T1: READ saldo = 100 T2: UPDATE saldo = 50 T1: UPDATE saldo = saldo + 10 = 110 (debería ser 60!)

Implementación: Locks, MVCC (Multi-Version Concurrency Control)

💾 Durability (Durabilidad)

Principio: Una vez confirmada, una transacción persiste permanentemente.

-- Garantías de durabilidad 1. Write-ahead logging (WAL) 2. Force-write to disk antes de COMMIT 3. Redundancia (RAID, replicación) 4. Backups regulares -- Incluso si el servidor se apaga inmediatamente después de COMMIT, -- los cambios deben persistir al reiniciar

Implementación: WAL, fsync(), replicación síncrona

Análisis Detallado: BASE

🌐 Basically Available

Principio: El sistema garantiza disponibilidad, pero puede tener fallos parciales.

// Ejemplo: Sistema de comentarios // Incluso si algunos nodos están caídos, // los usuarios pueden seguir comentando if (primary_node.isAvailable()) { return primary_node.addComment(comment); } else if (secondary_node.isAvailable()) { return secondary_node.addComment(comment); } else { return queue.addToRetryQueue(comment); }

Implementación: Múltiples réplicas, failover automático, graceful degradation

🌊 Soft State

Principio: El estado del sistema puede cambiar sin input externo debido a propagación de cambios.

// Ejemplo: Contador de likes // El valor puede cambiar mientras lo observas // debido a propagación de otros nodos Node A: likes = 100 Node B: likes = 98 (propagación pendiente) Node C: likes = 102 (propagación pendiente) // Después de un tiempo, todos convergen a 105

Implementación: Propagación asíncrona, timestamps, conflict resolution

⏰ Eventual Consistency

Principio: Si no hay nuevas actualizaciones, eventualmente todos los nodos tendrán el mismo valor.

// Ejemplo: Actualización de perfil 1. Usuario actualiza bio en Node A 2. Node A confirma inmediatamente 3. Cambio se propaga asíncronamente a Node B, C, D 4. Durante propagación: lecturas pueden ver bio antigua 5. Después de propagación: todas las lecturas ven bio nueva // Tiempo de convergencia: segundos a minutos

Implementación: Vector clocks, merkle trees, anti-entropy protocols

Comparación Práctica

Aspecto ACID BASE
Casos de Uso Sistemas financieros, inventarios, reservas Redes sociales, catálogos, analytics
Escalabilidad Limitada (vertical principalmente) Excelente (horizontal)
Performance Menor (overhead de consistencia) Mayor (operaciones asíncronas)
Complejidad Baja (modelo familiar) Alta (manejo de inconsistencias)
Disponibilidad Puede verse afectada Alta (fault-tolerant)
Consistencia Inmediata y fuerte Eventual

🏗️Clustering y Replicación

Conceptos Fundamentales

El clustering y la replicación son técnicas complementarias para lograr alta disponibilidad, escalabilidad y durabilidad en sistemas distribuidos.

🏗️ Clustering

Definición: Grupo de servidores que trabajan juntos como un sistema único.

Objetivo: Distribuir carga, eliminar puntos únicos de falla, facilitar escalamiento.

Tipos: Active-Active, Active-Passive, Load-balanced

🔄 Replicación

Definición: Mantener copias idénticas de datos en múltiples ubicaciones.

Objetivo: Durabilidad, disponibilidad, performance de lecturas.

Tipos: Síncrona, Asíncrona, Semi-síncrona

Topologías de Clustering

1. ACTIVE-ACTIVE CLUSTER ┌─────────┐ ┌─────────┐ ┌─────────┐ │ Node A │◄──►│ Node B │◄──►│ Node C │ │(Active) │ │(Active) │ │(Active) │ └─────────┘ └─────────┘ └─────────┘ Características: - Todos los nodos procesan requests - Load balancer distribuye tráfico - Máximo aprovechamiento de recursos - Complejidad en sincronización 2. ACTIVE-PASSIVE CLUSTER ┌─────────┐ ┌─────────┐ ┌─────────┐ │ Node A │───►│ Node B │───►│ Node C │ │(Active) │ │(Standby)│ │(Standby)│ └─────────┘ └─────────┘ └─────────┘ Características: - Solo un nodo activo a la vez - Failover automático a standby - Recursos subutilizados - Simplicidad en consistencia 3. MASTER-SLAVE CLUSTER ┌─────────┐ ┌─────────┐ ┌─────────┐ │ Master │───►│ Slave 1 │ │ Slave 2 │ │(Write) │ │ (Read) │ │ (Read) │ └─────────┘ └─────────┘ └─────────┘ Características: - Master maneja escrituras - Slaves manejan lecturas - Escalabilidad de lecturas - Write bottleneck en master

Tipos de Replicación

⚡ Replicación Síncrona

Proceso: Escritura espera confirmación de todas las réplicas antes de confirmar al cliente.

Flujo de escritura síncrona: 1. Cliente envía escritura a Master 2. Master envía a todas las réplicas 3. Master espera ACK de todas las réplicas 4. Master confirma al cliente 5. Escritura visible en todas las réplicas Tiempo total = max(latencia_replica_1, latencia_replica_2, ...)

Ventajas: Consistencia fuerte, cero pérdida de datos

Desventajas: Latencia alta, disponibilidad reducida

🌊 Replicación Asíncrona

Proceso: Escritura se confirma inmediatamente, replicación ocurre en background.

Flujo de escritura asíncrona: 1. Cliente envía escritura a Master 2. Master confirma inmediatamente al cliente 3. Master envía a réplicas en background 4. Réplicas procesan cuando pueden 5. Eventual consistency entre réplicas Tiempo de respuesta = latencia_master únicamente

Ventajas: Latencia baja, alta disponibilidad

Desventajas: Posible pérdida de datos, inconsistencia temporal

⚖️ Replicación Semi-síncrona

Proceso: Espera confirmación de un subconjunto de réplicas (quorum).

Flujo de escritura semi-síncrona (quorum = 2 de 3): 1. Cliente envía escritura a Master 2. Master envía a 3 réplicas 3. Master espera ACK de 2 réplicas (quorum) 4. Master confirma al cliente 5. Tercera réplica se actualiza asíncronamente Balance entre consistencia y performance

Ventajas: Balance entre consistencia y performance

Desventajas: Complejidad de configuración

Ejemplo: Cluster MongoDB Replica Set

// Configuración de Replica Set con 3 nodos // Arquitectura: 1 Primary + 2 Secondary Configuración inicial: rs.initiate({ _id: "myReplicaSet", members: [ { _id: 0, host: "mongo1:27017", priority: 2 }, // Primary preferido { _id: 1, host: "mongo2:27017", priority: 1 }, // Secondary { _id: 2, host: "mongo3:27017", priority: 1 } // Secondary ] }); Comportamiento normal: - mongo1 es Primary (recibe escrituras) - mongo2 y mongo3 son Secondary (replican datos) - Lecturas pueden ir a cualquier nodo (configurable) Escenarios de fallo: 1. Primary (mongo1) falla: - mongo2 o mongo3 se convierte en Primary automáticamente - Elección por mayoría (2 de 3 nodos) - Downtime: ~10-30 segundos 2. Secondary (mongo2) falla: - Sistema sigue operando normalmente - Solo 2 nodos disponibles para elección - Riesgo si falla otro nodo 3. Partición de red: - Si Primary queda aislado → se convierte en Secondary - Mayoría (2 nodos) elige nuevo Primary - Previene split-brain Configuración de Write Concern: db.collection.insertOne( { name: "Juan", email: "juan@email.com" }, { writeConcern: { w: "majority", j: true, wtimeout: 5000 } } ); // w: "majority" = espera confirmación de mayoría de nodos // j: true = espera que se escriba al journal (durabilidad) // wtimeout: 5000 = timeout de 5 segundos

Patrones Avanzados de Clustering

🌍 Multi-Master

Concepto: Múltiples nodos pueden aceptar escrituras

Ejemplo: CouchDB, Riak

Desafío: Resolución de conflictos

🔄 Ring Architecture

Concepto: Nodos organizados en anillo lógico

Ejemplo: Cassandra, Riak

Beneficio: Distribución uniforme

📊 Federated Clusters

Concepto: Múltiples clusters coordinados

Ejemplo: Kubernetes Federation

Uso: Multi-región, multi-cloud

🎯 Consensus-based

Concepto: Algoritmos de consenso (Raft, Paxos)

Ejemplo: etcd, Consul

Garantía: Consistencia fuerte

📊Estrategias de Particionamiento

¿Qué es el Particionamiento?

El particionamiento (sharding) es la técnica de dividir un gran conjunto de datos en fragmentos más pequeños (particiones o shards) que se distribuyen a través de múltiples nodos. Es fundamental para lograr escalabilidad horizontal.

🎯 Objetivos del Particionamiento

  • Escalabilidad: Distribuir carga entre múltiples nodos
  • Performance: Paralelizar operaciones
  • Disponibilidad: Aislar fallos a particiones específicas
  • Gestión: Facilitar mantenimiento y backups

Estrategias de Particionamiento

🔢 Range Partitioning

Método: Dividir por rangos de valores

Ejemplo: Usuarios A-H en Nodo 1, I-P en Nodo 2, Q-Z en Nodo 3

Ventaja: Consultas por rango eficientes

Desventaja: Distribución desigual (hotspots)

🎲 Hash Partitioning

Método: Usar función hash para determinar partición

Ejemplo: hash(user_id) % 3 determina el nodo

Ventaja: Distribución uniforme

Desventaja: Consultas por rango ineficientes

📁 Directory Partitioning

Método: Servicio de lookup mantiene mapeo

Ejemplo: Tabla de mapeo: user_123 → Nodo 2

Ventaja: Flexibilidad total

Desventaja: Punto único de falla en directorio

🔄 Consistent Hashing

Método: Hash ring con nodos y datos

Ejemplo: Usado por Cassandra, DynamoDB

Ventaja: Rebalanceo mínimo al agregar nodos

Desventaja: Complejidad de implementación

🏢 Functional Partitioning

Método: Dividir por funcionalidad/dominio

Ejemplo: Usuarios en DB1, Productos en DB2, Pedidos en DB3

Ventaja: Aislamiento de dominios

Desventaja: Consultas cross-domain complejas

🌍 Geographic Partitioning

Método: Dividir por ubicación geográfica

Ejemplo: Usuarios de América en US, Europa en EU, Asia en AS

Ventaja: Latencia reducida, compliance legal

Desventaja: Distribución desigual por región

Ejemplo Detallado: E-commerce con Hash Partitioning

// Configuración: 3 nodos para tabla de usuarios // Función hash: MD5(user_id) % 3 Ejemplos de distribución: user_12345 → MD5("12345") = "827ccb0eea8a706c4c34a16891f84e7b" → Último dígito 'b' (11 en hex) % 3 = 2 → Nodo 2 user_67890 → MD5("67890") = "03c7c0ace395d80182db07ae2c30f034" → Último dígito '4' % 3 = 1 → Nodo 1 user_11111 → MD5("11111") = "b59c67bf196a4758191e42f76670ceba" → Último dígito 'a' (10 en hex) % 3 = 1 → Nodo 1 Consultas: - Buscar user_12345: Calcular hash → Ir directamente a Nodo 2 - Buscar todos los usuarios: Consultar los 3 nodos y agregar resultados - Agregar nuevo nodo: Requiere re-sharding (problema del hash partitioning) Ventajas: ✅ Distribución uniforme ✅ Lookup O(1) ✅ Sin hotspots Desventajas: ❌ Re-sharding costoso ❌ Consultas por rango ineficientes ❌ Joins distribuidos complejos

Consistent Hashing: Solución al Re-sharding

Problema del Hash Partitioning tradicional: - Con 3 nodos: hash(key) % 3 - Agregar 1 nodo: hash(key) % 4 - Resultado: ~75% de los datos deben moverse Solución: Consistent Hashing 1. Crear un "ring" de hash values (0 to 2^32-1) 2. Colocar nodos en posiciones del ring 3. Cada key va al próximo nodo en sentido horario 4. Agregar nodo: solo afecta keys entre el nuevo nodo y el anterior Ejemplo: Ring positions: 0 -------- 2^32-1 Nodos: A(100), B(200), C(300) key_x → hash = 150 → va a nodo B (próximo en sentido horario) key_y → hash = 250 → va a nodo C key_z → hash = 50 → va a nodo A Agregar nodo D(175): - Solo keys entre 100 y 175 se mueven de B a D - ~25% de movimiento vs ~75% en hash tradicional Tecnologías que lo usan: - Amazon DynamoDB - Apache Cassandra - Redis Cluster - Riak

Problemas Comunes y Soluciones

Problema Descripción Soluciones
Hotspots Algunas particiones reciben más carga Hash partitioning, virtual nodes, re-sharding
Cross-shard Queries Consultas que abarcan múltiples particiones Denormalización, índices globales, query routing
Rebalancing Redistribuir datos al agregar/quitar nodos Consistent hashing, virtual nodes, gradual migration
Transacciones ACID a través de múltiples particiones 2PC, Saga pattern, eventual consistency

🔢Parámetros N, R, W

Introducción a los Parámetros

Los parámetros N, R, W son fundamentales para configurar el comportamiento de consistencia y disponibilidad en sistemas distribuidos, especialmente en bases de datos NoSQL como Cassandra y DynamoDB.

Definiciones

N = Número total de réplicas
R = Número de réplicas que deben responder para una lectura
W = Número de réplicas que deben confirmar una escritura

R + W > N = Strong Consistency
R + W ≤ N = Eventual Consistency

Análisis Detallado de cada Parámetro

🔢 N (Replication Factor)

Definición: Número total de copias de cada dato en el cluster.

Ejemplos comunes: N = 1: Sin replicación (peligroso) N = 3: Configuración estándar (balance costo/disponibilidad) N = 5: Alta disponibilidad (más caro) Consideraciones: - Mayor N = Mayor disponibilidad + Mayor costo - N impar evita split-brain scenarios - N debe ser ≤ número de nodos disponibles

📖 R (Read Consistency Level)

Definición: Cuántas réplicas deben responder para considerar una lectura exitosa.

Opciones comunes: R = 1: Lectura rápida, posible inconsistencia R = 2: Balance entre velocidad y consistencia R = N: Lectura más lenta, máxima consistencia Casos de uso: R = 1: Feeds de redes sociales, catálogos R = QUORUM: Datos importantes pero no críticos R = ALL: Datos financieros, inventarios críticos

✍️ W (Write Consistency Level)

Definición: Cuántas réplicas deben confirmar una escritura para considerarla exitosa.

Opciones comunes: W = 1: Escritura rápida, riesgo de pérdida W = 2: Balance entre velocidad y durabilidad W = N: Escritura lenta, máxima durabilidad Casos de uso: W = 1: Logs, métricas, datos no críticos W = QUORUM: Datos de aplicación estándar W = ALL: Transacciones financieras críticas

Configuraciones Comunes y sus Trade-offs

Configuración N, R, W Consistencia Disponibilidad Performance Caso de Uso
Fast Writes N=3, R=2, W=1 Eventual Alta Escrituras rápidas Logs, métricas, eventos
Fast Reads N=3, R=1, W=2 Eventual Alta Lecturas rápidas Catálogos, feeds, cache
Balanced N=3, R=2, W=2 Strong Media Balanceada Aplicaciones generales
Strong Consistency N=3, R=3, W=3 Strong Baja Lenta Datos financieros críticos
High Availability N=5, R=1, W=1 Eventual Muy Alta Muy rápida Sistemas 24/7 críticos

Ejemplo Práctico: Sistema de E-commerce

Configuración del cluster: - 5 nodos distribuidos geográficamente - N = 3 (cada dato replicado 3 veces) Diferentes configuraciones por tipo de dato: 1. CATÁLOGO DE PRODUCTOS (lectura intensiva) Configuración: N=3, R=1, W=2 Justificación: - Lecturas muy rápidas (solo 1 nodo responde) - Escrituras durables (2 nodos confirman) - Consistencia eventual aceptable para catálogo Comportamiento: - Usuario ve productos inmediatamente - Actualización de precio puede tardar segundos en propagarse - Disponible incluso si 2 nodos fallan 2. INVENTARIO (balance crítico) Configuración: N=3, R=2, W=2 Justificación: - Strong consistency (R+W > N) - Balance entre performance y consistencia - Evita overselling Comportamiento: - Lecturas ven escrituras recientes - Escrituras esperan confirmación de mayoría - Disponible si máximo 1 nodo falla 3. TRANSACCIONES DE PAGO (crítico) Configuración: N=3, R=3, W=3 Justificación: - Máxima consistencia y durabilidad - Cero tolerancia a pérdida de datos - Performance secundaria a integridad Comportamiento: - Todas las réplicas deben confirmar - Latencia mayor pero datos seguros - No disponible si cualquier nodo falla Monitoreo y alertas: - Latencia P99 por tipo de operación - Tasa de éxito por consistency level - Alertas si availability < SLA

📈Estrategias de Escalamiento

Escalamiento Vertical vs Horizontal

El escalamiento es fundamental para manejar el crecimiento de datos y usuarios. Existen dos enfoques principales, cada uno con sus ventajas y limitaciones:

⬆️ Escalamiento Vertical (Scale Up)

Definición: Aumentar la capacidad de un servidor individual (más CPU, RAM, almacenamiento).

Ejemplo de progresión: Servidor inicial: 4 CPU, 16GB RAM, 1TB SSD Escalamiento 1: 8 CPU, 32GB RAM, 2TB SSD Escalamiento 2: 16 CPU, 64GB RAM, 4TB SSD Escalamiento 3: 32 CPU, 128GB RAM, 8TB SSD Límites físicos: - CPU: ~128 cores en servidores high-end - RAM: ~4TB en configuraciones extremas - Storage: ~100TB en arrays SSD - Costo: Exponencial ($10K → $100K → $1M+)

Ventajas: Simplicidad, no cambios en aplicación, ACID completo

Desventajas: Límites físicos, costo exponencial, punto único de falla

➡️ Escalamiento Horizontal (Scale Out)

Definición: Agregar más servidores al sistema para distribuir la carga.

Ejemplo de progresión: Configuración inicial: 1 servidor Escalamiento 1: 3 servidores (cluster) Escalamiento 2: 10 servidores Escalamiento 3: 100 servidores Escalamiento 4: 1000+ servidores (Google, Facebook) Beneficios lineales: - Capacidad: N servidores = N × capacidad individual - Costo: Lineal con hardware commodity - Disponibilidad: Fault tolerance aumenta - Flexibilidad: Agregar/quitar nodos dinámicamente

Ventajas: Escalabilidad ilimitada, costo lineal, alta disponibilidad

Desventajas: Complejidad, consistencia eventual, cambios en aplicación

Patrones de Escalamiento Horizontal

🔄 Master-Slave Replication

Patrón: Un nodo maestro para escrituras, múltiples esclavos para lecturas

Escalabilidad: Solo lecturas (write bottleneck en master)

Ejemplo: MySQL con read replicas

🌐 Master-Master Replication

Patrón: Múltiples nodos pueden recibir escrituras

Escalabilidad: Lecturas y escrituras

Problema: Conflictos de escritura, split-brain

📊 Sharding/Partitioning

Patrón: Dividir datos entre múltiples nodos

Escalabilidad: Lecturas y escrituras lineales

Complejidad: Query routing, rebalancing

🏗️ Microservices Architecture

Patrón: Dividir aplicación por dominios funcionales

Escalabilidad: Independiente por servicio

Beneficio: Tecnologías específicas por dominio

Ejemplo: Evolución de Escalamiento en Startup

FASE 1: MVP (0-1K usuarios) Arquitectura: Monolito + PostgreSQL en 1 servidor Costo: $100/mes Limitaciones: ~1K usuarios concurrentes Bottleneck: CPU del servidor único FASE 2: Crecimiento (1K-10K usuarios) Arquitectura: App server + DB server separados Escalamiento: Vertical (más CPU/RAM) Costo: $500/mes Limitaciones: ~10K usuarios concurrentes Bottleneck: Base de datos (escrituras) FASE 3: Escalamiento inicial (10K-100K usuarios) Arquitectura: Load balancer + múltiples app servers + DB master-slave Escalamiento: Horizontal para app, vertical para DB Costo: $2K/mes Limitaciones: ~100K usuarios concurrentes Bottleneck: DB master (escrituras) FASE 4: Distribución (100K-1M usuarios) Arquitectura: Microservicios + sharded databases + cache layer Escalamiento: Horizontal completo Costo: $20K/mes Limitaciones: ~1M usuarios concurrentes Bottleneck: Complejidad operacional FASE 5: Hiperescala (1M+ usuarios) Arquitectura: Multi-región + CDN + NoSQL + event streaming Escalamiento: Global distribution Costo: $200K+/mes Limitaciones: Principalmente organizacionales Bottleneck: Coordinación entre equipos
