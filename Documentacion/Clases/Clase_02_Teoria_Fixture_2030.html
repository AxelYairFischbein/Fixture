Recordatorio: Los 6 Tipos de NoSQL

  • Documentales: Flexibilidad de esquema (MongoDB)
  • Grafos: Relaciones complejas (Neo4j)
  • Clave-Valor: Velocidad extrema (Redis)

📄Bases de Datos Documentales

🍃 MongoDB - Líder del Mercado

Modelo: Documentos BSON (Binary JSON)
Lenguaje: MongoDB Query Language (MQL)
Transacciones: ACID desde v4.0

Características Técnicas

  • Almacenamiento: Documentos BSON con esquema flexible
  • Índices: Secundarios, compuestos, geoespaciales, texto
  • Consultas: Agregation Pipeline para análisis complejos
  • Escalabilidad: Sharding automático
  • Replicación: Replica Sets con failover automático

Ejemplo Práctico: E-commerce

// Documento de producto con esquema flexible { "_id": ObjectId("507f1f77bcf86cd799439011"), "nombre": "iPhone 15 Pro", "categoria": ["smartphone", "apple", "premium"], "precio": { "valor": 999.99, "moneda": "USD", "descuentos": [ {"tipo": "estudiante", "porcentaje": 10} ] }, "especificaciones": { "pantalla": "6.1 pulgadas Super Retina XDR", "procesador": "A17 Pro", "almacenamiento": ["128GB", "256GB", "512GB", "1TB"], "camara": { "principal": "48MP", "ultra_angular": "12MP", "teleobjetivo": "12MP" } }, "reviews": [ { "usuario_id": "user_123", "rating": 5, "comentario": "Excelente teléfono, muy rápido", "fecha": ISODate("2024-01-15"), "verificado": true } ], "metadata": { "fecha_creacion": ISODate("2024-01-01"), "ultima_actualizacion": ISODate("2024-01-15"), "stock": 150, "activo": true, "tags": ["nuevo", "popular", "oferta"] } } // Consulta con agregación db.productos.aggregate([ { $match: { "categoria": "smartphone", "precio.valor": { $lt: 1000 } } }, { $unwind: "$reviews" }, { $group: { _id: "$_id", nombre: { $first: "$nombre" }, rating_promedio: { $avg: "$reviews.rating" }, total_reviews: { $sum: 1 } }}, { $sort: { rating_promedio: -1 } }, { $limit: 10 } ])

Casos de Uso Ideales

✅ Excelente para:

  • Aplicaciones web con datos JSON
  • Catálogos de productos variables
  • Sistemas de gestión de contenido
  • APIs REST y microservicios
  • Prototipado rápido

❌ No recomendado para:

  • Transacciones financieras críticas
  • Datos altamente relacionales
  • Consultas complejas con múltiples JOINs
  • Aplicaciones que requieren SQL estricto

🕸️Bases de Datos de Grafos

🔗 Neo4j - Líder en Grafos

Modelo: Nodos, Relaciones y Propiedades
Lenguaje: Cypher Query Language
Transacciones: ACID completas

Características Técnicas

  • Modelo: Property Graph con nodos y relaciones tipadas
  • Índices: Automáticos en propiedades, full-text search
  • Algoritmos: PageRank, Shortest Path, Community Detection
  • Visualización: Neo4j Browser integrado
  • Escalabilidad: Clustering (Enterprise)

Ejemplo Práctico: Red Social Profesional

// Creación de nodos y relaciones CREATE (juan:Usuario { nombre: "Juan Pérez", edad: 28, ciudad: "Buenos Aires", profesion: "Developer", skills: ["JavaScript", "Python", "React"] }) CREATE (maria:Usuario { nombre: "María González", edad: 26, ciudad: "Córdoba", profesion: "Data Scientist", skills: ["Python", "R", "Machine Learning"] }) CREATE (google:Empresa { nombre: "Google", sector: "Tecnología", empleados: 150000, fundacion: 1998 }) CREATE (mit:Universidad { nombre: "MIT", pais: "USA", ranking: 1, tipo: "Privada" }) // Crear relaciones con propiedades CREATE (juan)-[:AMIGO_DE {desde: date("2020-01-15"), tipo: "cercano"}]->(maria) CREATE (maria)-[:TRABAJA_EN { puesto: "Senior Data Scientist", desde: date("2023-06-01"), salario: 120000 }]->(google) CREATE (maria)-[:ESTUDIO_EN { titulo: "Computer Science", año: 2022, gpa: 3.9 }]->(mit) // Consultas complejas de relaciones // Encontrar amigos de Juan que trabajan en tecnología MATCH (juan:Usuario {nombre: "Juan Pérez"})-[:AMIGO_DE]-(amigo) -[:TRABAJA_EN]-(empresa:Empresa {sector: "Tecnología"}) RETURN amigo.nombre, empresa.nombre, amigo.profesion // Recomendaciones: personas con skills similares MATCH (juan:Usuario {nombre: "Juan Pérez"}) MATCH (otros:Usuario) WHERE juan <> otros AND any(skill IN juan.skills WHERE skill IN otros.skills) RETURN otros.nombre, [skill IN juan.skills WHERE skill IN otros.skills] as skills_comunes, size([skill IN juan.skills WHERE skill IN otros.skills]) as coincidencias ORDER BY coincidencias DESC LIMIT 5 // Análisis de influencia con PageRank CALL gds.pageRank.stream('usuarios-graph') YIELD nodeId, score RETURN gds.util.asNode(nodeId).nombre as usuario, score ORDER BY score DESC LIMIT 10

Casos de Uso Ideales

✅ Excelente para:

  • Redes sociales y profesionales
  • Sistemas de recomendación
  • Detección de fraude
  • Análisis de dependencias
  • Gestión de conocimiento

❌ No recomendado para:

  • Datos tabulares simples
  • Operaciones CRUD básicas
  • Grandes volúmenes sin relaciones
  • Aplicaciones con pocos vínculos

🔑Bases de Datos Clave-Valor

⚡ Redis - Velocidad Extrema

Modelo: In-Memory Key-Value Store
Estructuras: Strings, Hashes, Lists, Sets, Sorted Sets
Persistencia: RDB + AOF

Características Técnicas

  • Almacenamiento: Completamente en memoria (RAM)
  • Estructuras: Tipos de datos avanzados más allá de string
  • Persistencia: Snapshots (RDB) y Append-Only File (AOF)
  • Pub/Sub: Sistema de mensajería integrado
  • Clustering: Redis Cluster para escalabilidad

📊Bases de Datos Columnares

🏛️ Cassandra - Escalabilidad Masiva

Modelo: Wide Column Store
Lenguaje: CQL (Cassandra Query Language)
Arquitectura: Distribuida sin maestro

Características Técnicas

  • Arquitectura: Peer-to-peer sin punto único de falla
  • Consistencia: Configurable (ONE, QUORUM, ALL)
  • Particionamiento: Automático basado en hash
  • Replicación: Multi-datacenter
  • Compresión: Algoritmos optimizados para columnas

Ejemplo Práctico: Sistema IoT Smart City

-- === MODELADO DE DATOS === -- Tabla para datos de sensores IoT CREATE KEYSPACE smart_city WITH replication = { 'class': 'NetworkTopologyStrategy', 'datacenter1': 3, 'datacenter2': 2 }; USE smart_city; -- Tabla optimizada para series temporales CREATE TABLE sensor_data ( sensor_id UUID, timestamp TIMESTAMP, sensor_type TEXT, ubicacion TEXT, temperatura DOUBLE, humedad DOUBLE, calidad_aire INT, ruido_db DOUBLE, metadata MAP, PRIMARY KEY (sensor_id, timestamp) ) WITH CLUSTERING ORDER BY (timestamp DESC) AND compaction = {'class': 'TimeWindowCompactionStrategy'} AND gc_grace_seconds = 86400; -- Tabla para alertas por ubicación CREATE TABLE alertas_por_ubicacion ( ubicacion TEXT, fecha DATE, timestamp TIMESTAMP, sensor_id UUID, tipo_alerta TEXT, severidad INT, descripcion TEXT, PRIMARY KEY ((ubicacion, fecha), timestamp) ) WITH CLUSTERING ORDER BY (timestamp DESC); -- === INSERCIÓN DE DATOS === -- Insertar datos de sensores (alta frecuencia) INSERT INTO sensor_data ( sensor_id, timestamp, sensor_type, ubicacion, temperatura, humedad, calidad_aire, ruido_db, metadata ) VALUES ( uuid(), '2024-01-15 10:30:00', 'ambiental', 'Plaza San Martin', 23.5, 65.2, 85, 45.3, {'zona': 'centro', 'tipo_via': 'peatonal'} ); -- Batch insert para alta performance BEGIN BATCH INSERT INTO sensor_data (...) VALUES (...); INSERT INTO sensor_data (...) VALUES (...); INSERT INTO sensor_data (...) VALUES (...); APPLY BATCH; -- === CONSULTAS OPTIMIZADAS === -- Datos de un sensor en las últimas 24 horas SELECT timestamp, temperatura, humedad, calidad_aire FROM sensor_data WHERE sensor_id = 123e4567-e89b-12d3-a456-426614174000 AND timestamp >= '2024-01-14 10:30:00' AND timestamp < '2024-01-15 10:30:00' ORDER BY timestamp DESC; -- Alertas por ubicación en el último mes SELECT timestamp, tipo_alerta, severidad, descripcion FROM alertas_por_ubicacion WHERE ubicacion = 'Plaza San Martin' AND fecha >= '2024-01-01' AND fecha <= '2024-01-31' ORDER BY timestamp DESC LIMIT 100; -- === AGREGACIONES CON SPARK === -- Análisis con Spark Connector SELECT ubicacion, AVG(temperatura) as temp_promedio, MAX(calidad_aire) as max_calidad_aire, COUNT(*) as total_lecturas FROM sensor_data WHERE timestamp >= '2024-01-01' AND timestamp < '2024-02-01' GROUP BY ubicacion;

✅ Excelente para:

❌ No recomendado para:

🎯Bases de Datos de Objetos

🔷 InterSystems IRIS - Multi-Modelo

Modelo: Objetos nativos + Multi-modelo
Lenguajes: ObjectScript, SQL, Python, Java
Transacciones: ACID completas

Características Técnicas

  • Multi-modelo: Objetos, relacional, documentos, key-value
  • Performance: Almacenamiento optimizado en memoria y disco
  • Interoperabilidad: APIs para múltiples lenguajes
  • Escalabilidad: Sharding y clustering enterprise
  • Analytics: OLAP integrado y machine learning

📈Bases de Datos Multidimensionales

📊 InfluxDB - Series Temporales

Modelo: Time Series optimizado
Lenguaje: InfluxQL / Flux
Compresión: Algoritmos específicos para tiempo

Características Técnicas

  • Optimización temporal: Índices y compresión específicos
  • Retención automática: Políticas de eliminación por tiempo
  • Agregaciones: Funciones estadísticas integradas
  • Downsampling: Reducción automática de resolución
  • Alertas: Sistema de monitoreo integrado

Ejemplo Práctico: Monitoreo de Infraestructura

// === ESTRUCTURA DE DATOS === // Measurement: cpu_usage // Tags: host, region, environment // Fields: usage_percent, load_average // Timestamp: automático // === INSERCIÓN DE DATOS === // Usando Line Protocol cpu_usage,host=server01,region=us-east,environment=prod usage_percent=85.2,load_average=1.5 1642248600000000000 cpu_usage,host=server02,region=us-east,environment=prod usage_percent=72.1,load_average=1.2 1642248600000000000 memory_usage,host=server01,region=us-east,environment=prod used_percent=68.5,available_gb=12.8 1642248600000000000 // Usando API HTTP POST /api/v2/write?org=myorg&bucket=metrics Content-Type: text/plain cpu_usage,host=server01,region=us-east usage_percent=85.2 1642248600000000000 memory_usage,host=server01,region=us-east used_percent=68.5 1642248600000000000 // === CONSULTAS CON FLUX === // CPU promedio por host en la última hora from(bucket: "metrics") |> range(start: -1h) |> filter(fn: (r) => r._measurement == "cpu_usage") |> filter(fn: (r) => r._field == "usage_percent") |> group(columns: ["host"]) |> mean() // Detección de anomalías from(bucket: "metrics") |> range(start: -24h) |> filter(fn: (r) => r._measurement == "cpu_usage") |> filter(fn: (r) => r._field == "usage_percent") |> aggregateWindow(every: 5m, fn: mean) |> movingAverage(n: 12) // Promedio móvil de 1 hora |> map(fn: (r) => ({ r with anomaly: if r._value > 90.0 then "HIGH" else "NORMAL" })) // Comparación período anterior import "date" current = from(bucket: "metrics") |> range(start: -1h) |> filter(fn: (r) => r._measurement == "cpu_usage") |> mean() previous = from(bucket: "metrics") |> range(start: -2h, stop: -1h) |> filter(fn: (r) => r._measurement == "cpu_usage") |> mean() join(tables: {current: current, previous: previous}, on: ["host"]) |> map(fn: (r) => ({ host: r.host, current_cpu: r._value_current, previous_cpu: r._value_previous, change_percent: (r._value_current - r._value_previous) / r._value_previous * 100.0 })) // === POLÍTICAS DE RETENCIÓN === // Datos en tiempo real: 7 días // Datos agregados por hora: 30 días // Datos agregados por día: 1 año // Configuración de downsampling automático option task = { name: "downsample-cpu", every: 1h, } from(bucket: "metrics") |> range(start: -1h) |> filter(fn: (r) => r._measurement == "cpu_usage") |> aggregateWindow(every: 1h, fn: mean) |> to(bucket: "metrics-hourly") // === ALERTAS === // Alerta por CPU alto from(bucket: "metrics") |> range(start: -5m) |> filter(fn: (r) => r._measurement == "cpu_usage") |> filter(fn: (r) => r._field == "usage_percent") |> mean() |> map(fn: (r) => ({ r with _level: if r._value > 90.0 then "crit" else if r._value > 80.0 then "warn" else "ok" })) |> filter(fn: (r) => r._level != "ok") |> to(bucket: "alerts")

⚖️Criterios de Selección

Marco de Decisión Sistemático

La selección de una base de datos NoSQL debe basarse en un análisis sistemático de múltiples factores. No existe una "mejor" tecnología universal, sino la más adecuada para cada contexto específico.

🎯 Criterios Técnicos

  • Modelo de datos: ¿Cómo se estructuran los datos?
  • Patrones de acceso: ¿Más lecturas o escrituras?
  • Escalabilidad: ¿Vertical u horizontal?
  • Consistencia: ¿ACID estricto o eventual?
  • Performance: ¿Latencia o throughput crítico?

🏢 Criterios Operacionales

  • Complejidad: ¿Facilidad de administración?
  • Ecosistema: ¿Herramientas disponibles?
  • Equipo: ¿Curva de aprendizaje?
  • Costo: ¿TCO total?
  • Soporte: ¿Comunidad y documentación?

Proceso de Evaluación

1. ANÁLISIS DE REQUERIMIENTOS ├── Identificar tipos de datos ├── Mapear patrones de acceso ├── Estimar volúmenes y crecimiento └── Definir SLAs de performance 2. FILTRADO INICIAL ├── Eliminar tecnologías incompatibles ├── Considerar restricciones presupuestarias ├── Evaluar capacidades del equipo └── Verificar requisitos de compliance 3. EVALUACIÓN DETALLADA ├── Crear matriz de decisión ├── Asignar pesos a criterios ├── Puntuar cada tecnología └── Calcular scores finales 4. VALIDACIÓN PRÁCTICA ├── Implementar POCs (Proof of Concept) ├── Medir performance real ├── Evaluar facilidad de desarrollo └── Estimar esfuerzo operacional 5. DECISIÓN FINAL ├── Comparar resultados cuantitativos ├── Considerar factores cualitativos ├── Evaluar riesgos y mitigaciones └── Documentar justificación

🎯Hito 2 — Matriz de Decisión del Fixture 2030

Entregable: Matriz de selección tecnológica

Sobre la base del diagnóstico realizado en el Hito 1, cada grupo deberá comparar los modelos NoSQL estudiados y justificar qué alternativa resulta más adecuada para cada necesidad de datos de la plataforma del Fixture del Mundial 2030.

Componentes de la entrega

1. SÍNTESIS DEL DIAGNÓSTICO INICIAL ├── Datos y necesidades priorizadas en el Hito 1 ├── Patrones de acceso y volúmenes relevantes └── Restricciones que condicionan la elección 2. MATRIZ DE DECISIÓN ├── Conjuntos de datos o subsistemas del Fixture 2030 ├── Modelos NoSQL candidatos ├── Criterios de selección definidos por el grupo ├── Ponderación y evaluación comparativa └── Resultado de cada decisión 3. JUSTIFICACIÓN TÉCNICA ├── Razones de la tecnología o modelo seleccionado ├── Ventajas para la necesidad analizada ├── Alternativas consideradas └── Trade-offs aceptados 4. MAPA DE PERSISTENCIA DEL PROYECTO ├── Relación entre necesidades de datos y decisiones tomadas ├── Responsabilidad prevista de cada modelo elegido └── Preguntas pendientes para las etapas de implementación

Criterios de Evaluación

📊 Matriz y trazabilidad (35%)

  • Relación clara con el diagnóstico del Hito 1
  • Criterios definidos y aplicados de forma consistente
  • Comparación completa de alternativas

⚖️ Justificación técnica (35%)

  • Uso correcto de las características de cada modelo
  • Decisiones fundamentadas en necesidades del Fixture
  • Reconocimiento explícito de trade-offs

🏗️ Coherencia del mapa de persistencia (20%)

  • Asignación razonada de responsabilidades
  • Compatibilidad con los objetivos de escala del escenario
  • Preguntas pendientes bien formuladas

📝 Calidad documental (10%)

  • Documento claro, completo y ordenado
  • Matriz legible y verificable
  • Terminología técnica utilizada con precisión
